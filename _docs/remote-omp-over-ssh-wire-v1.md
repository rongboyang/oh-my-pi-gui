# Remote omp over SSH: wire v1

This is the normative P0 behavior for Core and GUI. **MUST**, **MUST NOT**, and **SHOULD** describe interoperability requirements. The authoritative frame shapes, validation boundaries, error names, capabilities, and numeric limits are in [`remote-wire.ts`](../src/shared/remote-wire.ts); [`remote-wire.fixture.json`](../src/shared/remote-wire.fixture.json) supplies cross-repository examples. Remote v1 is independent of `rpc-ui` versions. Payloads deliberately typed as `unknown` retain their existing Core meaning; this protocol does not expose the full RPC surface.

## CLI and transport

- `omp remote serve --name <name>` runs in the intended workspace and owns the instance, Agent, private per-user registration and Unix socket. Canonical workspace is the absolute physical path obtained by resolving the startup directory and its symbolic links. Registration MUST be exclusive, private to the account, and removed only by its owner; duplicate live identity MUST fail. The endpoint MUST be available before initialization can wait for approval. Disconnecting an attach MUST NOT terminate the instance or its accepted work.
- `omp remote list --json` discovers only live instances of the logged-in account, verifies registration against the socket, and emits one JSON array of `RemoteInstance` objects on stdout on success. Stale registration or a reused PID alone is not proof of liveness. No live instances is exit 3, not an empty successful selection. No socket path or credentials are exposed. Listing does not acquire a lease.
- `omp remote attach --instance <key>` accepts only a stable instance key, verifies registration and peer identity, then bridges stdin/stdout to that existing instance using UTF-8 NDJSON, one JSON frame per line. It MUST NOT create, repair, replace, restart, or select another instance, accept a socket path or workspace override, or start a local fallback. The client explicitly selects among multiple listed instances. Attach stdout is protocol frames only; diagnostics go to stderr and MUST NOT contain message bodies, tool output, approval input, or credentials. List stdout contains only its JSON result; serve diagnostics go to stderr. Failed CLI commands emit diagnostics only on stderr, never a partial success result.
- CLI exit statuses are 0 for success, 2 for invalid usage, 3 for no live instance, 4 for wrong identity, 5 for incompatible protocol, and 1 for other operational failure. These are Core CLI statuses; OpenSSH's 255 is a transport/SSH failure, not a Core exit code. A failure after the protocol stream starts is reported by a structured reply where possible; EOF or a failed bridge is not evidence that an accepted operation failed.
- The GUI uses system OpenSSH with a structured target and fixed remote commands, no PTY or agent forwarding, and preserves host-key verification. Authentication and host-key prompts belong to the initiating attempt. It MUST NOT silently install Core, bypass authentication, or substitute a local instance.

## Identity and handshake

The stable `instanceKey` is the 64 lowercase hexadecimal characters of SHA-256 over the UTF-8 bytes of `JSON.stringify([name, canonicalWorkspace])`, with no additional normalization or newline. The same name and canonical workspace yield the same key; each serve startup generates a fresh opaque `epoch`. An instance and its sessions belong to the SSH account and bound workspace. A session ID is an opaque Core identifier, not a file path; a run ID identifies one run within its epoch and session. An action ID identifies one mutation within its epoch and session; an approval request ID identifies one pending approval in that same scope. Transport request IDs correlate replies on a connection and are distinct from action IDs; clients MUST avoid reusing an outstanding request ID. IDs from another target, connection generation, epoch, or session MUST NOT be routed into the current state.

The first frame is `hello`; the server replies with the same request ID. Both sides verify the expected instance key and canonical workspace against discovery and the connected peer, select remote version 1, and require all of `REMOTE_REQUIRED_CAPABILITIES` on both sides. Reject a wrong identity or incompatible version/capabilities rather than continuing. The negotiated frame limit is no greater than either peer's advertised limit and `REMOTE_MAX_FRAME_BYTES`; enforce it on incoming UTF-8 frame bytes before unbounded buffering or JSON parsing. Unknown capability strings are retained for forward negotiation, not treated as required features. `read_document` is optional: phase I MUST NOT require it or any other phase II capability.

## Lease, synchronization, and actions

1. After hello, `acquire` obtains the single active writer lease, a positive, increasing fencing number. A second client receives `busy` and MUST NOT preempt an unexpired lease. Send `heartbeat` with that lease at `REMOTE_LEASE_HEARTBEAT_MS`; EOF, explicit disconnect, or `REMOTE_LEASE_TIMEOUT_MS` without a valid heartbeat releases it. Core checks the current lease and epoch before accepting each mutation; stale commands are rejected even if delivered late. Lease loss does not cancel accepted work.
2. `sync` with the lease captures an authoritative snapshot and event sequence `S` at one state boundary, and subscribes to events starting at `S + 1`. The optional `resumeSessionId` identifies a saved session in the same workspace; it is not a path or permission to change cwd. A genuinely uninitialized instance may have a null snapshot session ID. Core assigns a session ID before awaiting an initialization approval that needs a response.
3. Initialization approvals MUST be discoverable in the snapshot while phase is `starting`; after handshake and acquisition, a client may answer a valid pending initialization approval before ordinary ready. All other mutations wait until initial synchronization and any uncertain-action reconciliation complete. Approval state and resolvers belong to the instance, not the connection: disconnect neither approves nor cancels them, although explicit tool timeouts or cancellation still apply. Validate lease, epoch, session, and request ID, then atomically claim the pending request; duplicates, unknown, cancelled, or expired requests cannot affect another approval.
4. Apply the snapshot before events, then apply only the same epoch and session's contiguous events after `S`, discarding already-applied frames. History and output pages are tied to the snapshot `view`, not event sequence numbers; clients use opaque cursors and do not assume a streaming session prevents paging. If a sequence gap, invalidated view, or synchronization buffer overflow occurs, discard that sync and obtain a new snapshot or reconnect. A slow connection MUST NOT block the Agent or silently drop events: close it on queue overflow. Reconnect starts from a fresh snapshot, not a presumed durable event replay.
5. `sessions` lists only the bound workspace. `new_session` and `open_session` use Core-owned session lookup and MUST NOT interrupt a running task or cross workspaces. The allowed mutations are the `RemoteActionCommand` variants only. Stop is explicit, scoped to the current epoch, session and `runId`, and succeeds only after Core confirms stopping that run; a late stop MUST NOT stop a subsequent run. Closing a tab or losing SSH is not stop.

Snapshots cover current phase, run, partial reply, tools and pending approvals. Completed results come from the remote session; running tool output is available through bounded output pages, including paths that would otherwise exist only as live events. When product output retention is exceeded, mark `truncated`; do not confuse truncation with an empty result or a synchronization failure.

## Receipts and recovery

Before sending any mutation, the client generates an `actionId` and records only the epoch, session and action ID needed for reconciliation, not a queued message or approval body. Core registers the action before dispatch and retains its receipt for `REMOTE_RECEIPT_RETENTION_MS`, subject to `REMOTE_MAX_RECEIPTS`. In that retention window, repeating the same scoped action ID with the same command returns the same receipt without executing it again; reusing it with a different command is rejected. `accepted` means registered, not completed; `succeeded` and `rejected` are terminal results; `unknown` means the outcome cannot be proven, not that the action did not run. A lost reply or timeout MUST NOT be interpreted as failure or trigger automatic replay.

After reconnect, reconcile outstanding IDs with `receipt` and the authoritative session/approval snapshot before enabling ordinary writes. If a receipt has expired, been evicted, or belongs to an old epoch and the result cannot be proven, display an unconfirmed result; never silently resend. Exactly-once across Core crashes or beyond the retention window is not promised. A changed epoch means the instance restarted: old runs, approvals, receipts and events MUST NOT be applied to the new epoch. Only saved sessions can be reopened; do not infer task completion or restart work.

## Failures and bounds

Use the stable codes in `REMOTE_ERROR_CODES`, not diagnostic text, for classification. `host_key_unknown`, `host_key_changed`, `auth_cancelled`, and `auth_failed` describe SSH trust/authentication; `cli_missing` means the remote command was not discoverable. `no_instance`, `identity_mismatch`, and `protocol_incompatible` require explicit user action rather than fallback. `busy` is a held lease; `stale_lease`, `stale_epoch`, `stale_session`, `stale_run`, and `unknown_request` reject stale or misrouted work. `unknown_result` denotes an unprovable outcome; `invalid_request` and `unsupported` describe invalid or unavailable operations. `overflow`, `disconnected`, `timeout`, and `internal_error` distinguish capacity, transport, timeout, and other failures. Preview-specific codes apply only to the optional phase II operation. Do not claim a remote task completed on disconnect.

Enforce the source constants for frame, ID, path, capabilities, versions, discovery list, page items and bytes, retained output, per-connection queue frames and bytes, receipts, and optional document size. A frame or queue limit violation is explicit (`overflow` where a reply is possible), never unlimited allocation or silent loss. Limit reconnects to `REMOTE_RECONNECT_MAX_ATTEMPTS` and backoff to `REMOTE_RECONNECT_MAX_DELAY_MS`; retry only recoverable transport failures, not cancellation, identity, or trust/authentication changes. Preserve the last known state as unconfirmed while disconnected.
